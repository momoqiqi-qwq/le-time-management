## 1. 状态与刷新：不用框架，这三件事就得自己做

先看整体分层的形状（本部分讨论①呈现层与④状态层之间那条边界）：
![软件层次总图](architecture/00-layers.svg)

### 1.1 所有写入必须走一个入口 🔴

**现象**：一个软件里如果"改数据"有十条路，那么"改完之后要落盘、要刷界面"这件事就有十条实现，
漏掉任何一条的表现都是**用户改了、界面也变了、重启之后没了**。

**根因**：界面刷新与持久化天然是两件不相干的事，写在调用点最顺手，也就最容易各写一半。

**解法**：`src/store.js` 是全前端唯一持有业务状态的模块，任何变更都必须经 `changed()` 这一个出口 ——
它同时负责广播刷新与排入落盘队列，所以**绕过它等于同时绕过这两件事**（`store.js:99-103`）：

```js
function changed() {
  if (batchDepth > 0) { batchDirty = true; return; }
  emitChanged();
  scheduleSave();
}
```

界面上没有任何"保存"按钮，就是这个函数在背后兜住。派生的写操作（`addTask`/`updateTask`/`addBlock`…）
全部以 `changed(); return x;` 收尾，形态一致。

**还有一个隐蔽分支**：只改内存不刷界面是不够的。`normalizeState()` 会剥掉历史遗留的
`settings.background`（那里面可能压着几百 KB 的 base64 图片），但剥的只是内存对象：

```js
// store.js:77-82
// 归一化剥掉 settings.background 只改了内存里的对象；不主动写一次的话，那份 base64 图片
// 会一直躺在数据文件里，直到用户下次改点什么才顺手落盘。导入路径（replaceAll）自带 changed()，
// 只有启动这条路径需要补这一下。
if (loaded && typeof loaded === "object" && loaded.settings && "background" in loaded.settings) {
  queueSave().catch(() => {});
}
```

**怎么锁住**：全前端只有 `store.js` 持有业务状态（`views/*` 与编排模块一律 `import * as S from "./store.js"`，
不保存任务/块的自有副本）；`ui.js` 与 `theme.js` 是纯外观叶子层，只写 CSS 变量、不碰数据。
落盘路径本身由 `scripts/test-store-cache.mjs` 用真 `store.js` + `localStorage` 替身跑通
（它同时是 1.4 的回归）。

### 1.2 高频编辑不能高频写盘：防抖 → 串行 → 原子替换

**现象**：改一次标题就写一次整个 JSON（当前数据规模下一次约几十 KB），打字会卡；
更糟的是两次写入并发时，磁盘上可能是**半截 JSON**。

**解法**：三段各解决一件事（`store.js:87-94`）。整条链路（界面 → `changed()` → 防抖 → 串行队列 →
Rust 原子替换）见图：

![存储链路](architecture/05-storage.svg)

```js
function queueSave() {
  saveChain = saveChain.catch(() => {}).then(() => api.saveData(state));
  return saveChain.then(() => { saveFail = 0; }).catch((e) => { if (++saveFail === 1) console.error("保存失败", e); throw e; });
}
function scheduleSave() {
  clearTimeout(saveTimer);
  saveTimer = setTimeout(() => { queueSave().catch(() => {}); }, 350);
}
```

- `scheduleSave` 350 ms 防抖：连续编辑 20 次只产生一次磁盘写入；
- `queueSave` 用 **Promise 链**把写入串成一条队：`saveChain = saveChain.then(...)`，两次落盘永不交错。
  `.catch(() => {})` 挂在前置段上是必要的 —— 一次失败不能让整条链永久 rejected；
- Rust 侧落盘是"写临时文件 + `fs::rename`"（`src-tauri/src/lib.rs:735-743`）：

```rust
let tmp = dir.join("data.json.tmp");
fs::write(&tmp, serde_json::to_vec_pretty(&data).unwrap())
    .map_err(|e| format!("写入临时文件失败: {e}"))?;
// 原子替换，避免写一半崩溃丢数据
fs::rename(&tmp, &path).map_err(|e| format!("替换数据文件失败: {e}"))?;
```

**退出时还有一次握手**：防抖里没落盘的最后一次改动，不能靠"退出前等一下"解决 ——
托盘"退出"广播 `app-quit`，前端把队列写完后调 `quit_ack` 回执，Rust 用条件变量等这个回执
（`lib.rs:1646` 发事件，`lib.rs:1605-1615` 等待，超时是硬上限，不会挂死）：

```rust
match gate.cv.wait_timeout_while(acked, std::time::Duration::from_millis(timeout_ms), |a| !*a) {
    Ok((guard, _)) => *guard,
    Err(_) => false,
}
```

**已知取舍**：这里没有 `fsync`。原子改名保证"读不到半截"，但不保证断电时的落盘顺序；
这条在设计篇 8.2 已列为知情取舍，兜底是本地环形自动备份。

### 1.3 批量改动的抖动：`batchChanges` 与 `persistSoon`

**现象**：自动化一次排 6 个任务，会产生 6 次"全界面刷新 + 6 次落盘排队"，肉眼看到的是闪烁，
实际成本是 6 次跨进程调用。另一头，拖滑块、拖侧栏这种高频设置如果每次 `changed()` 都刷界面，
会把跟随鼠标的那段动画拖成幻灯片。

**解法**：两个正交的小工具。

- `batchChanges(fn)`（`store.js:107-119`）在批量期间把 `batchDepth++`，期间 `changed()` 只置
  `batchDirty` 标志，最外层退出时**合并成一次**刷新 + 一次落盘。四条自动化规则全部经它执行
  （`automation.js:71-84`），所以"规则跑完一次"对界面来说就是一次变更。
- `persistSoon()`（`store.js:105`）**只请求落盘、不刷界面**，用于滑块位置、导航位置、音量这类
  "界面已经自己画过了"的高频设置。提醒的已发日志（幂等记录）也走它（`taskReminder.js:332`）。

**为什么不用一个通用的 dirty-check 层**：见 1.5。

### 1.4 派生数据要缓存，但不能缓存错：版本计数失效

**现象**：时间块画布、冲突试算、自动化都要"某一天的块，按开始时间排序"。每次都
`filter + sort` 全量数组，在几百块的学期数据上会在拖拽过程里被调上百次。

**解法**：按日期缓存 + **一个整数版本号**统一失效（`store.js:63-66`、`190-196`）：

```js
function invalidateBlockIndex() {
  blockIndexVersion++;
  blockIndexByDate.clear();
}
export function blocksOf(dateStr) {
  const cached = blockIndexByDate.get(dateStr);
  if (cached && cached.version === blockIndexVersion) return cached.blocks.slice();
  const blocks = state.blocks.filter((b) => b.date === dateStr).sort((a, b) => mmOf(a.start) - mmOf(b.start));
  blockIndexByDate.set(dateStr, { version: blockIndexVersion, blocks });
  return blocks.slice();
}
```

三处细节都是刻意的：缓存命中也 `slice()` 返回副本（调用方 `sort` 会原地改缓存数组）；
所有写块的路径（`addBlock`/`updateBlock`/`removeBlock`/`replaceAll`/`initStore`）**都必须**调
`invalidateBlockIndex()`，包括那些"看起来只改了别的字段"的 —— 所以 `updateTask` 不改块就不失效，
而 `removeTask` 会连带删块因此必须失效；版本号比对而不是时间戳，避免同一 tick 内的读写顺序歧义。

**怎么锁住**：`scripts/test-store-cache.mjs` 用真 `store.js` + `localStorage` 替身跑三条断言 ——
拿到缓存数组后 `pop()` 再读一次必须仍是原样（"blocksOf 返回副本，调用方不能改坏缓存"）、
`updateBlock` 改了 `start` 之后必须重新排序（"更新开始时间后缓存失效并重新排序"）。
第二条就是"某个写路径忘了调 `invalidateBlockIndex()`"的可执行探测器。

### 1.5 局部刷新的粒度：一格一个 `_refresh`，不做虚拟 DOM

**现象**：搜索框每输入一个字符都重建整个页面，输入就会掉字。

**解法**：进入任务表时只注册**一个**订阅，回调里分发给四格各自的刷新函数（`views/quadrant.js:365-368`）：

```js
const un = S.subscribe(() => {
  cells.forEach((c) => c._refresh && c._refresh());
  refreshChips();
});
container._unsub = un;
```

单格内部用 `replaceChildren()` 重建卡片列表，不做逐卡片增量 diff。**这是一个算过账的取舍**：
在数百任务的规模下，重建一格的代价（四格各自几十 DOM 节点）低于维护 diff 逻辑的复杂度成本，
而 diff 一旦有 bug 表现就是"该刷新的没刷新"，属于最难查的那类。

### 1.6 两个订阅者同时刷一次就会闪 🔴

**现象**：时间块页切到"日时间轴"以外视图时，整屏白一下。

**根因**：父视图（时间块页）和子视图（投影视图）**各自**订阅了 store。一次变更触发两个回调，
每个都重建自己那块 DOM，第二个重建时看到的是第一个刚建好、还没画上的一棵树。

**解法**：一个视图**只允许一个**订阅入口，子视图不订阅（`views/timeblock.js:332-345`）：

```js
function syncView() {
  const day = viewMode === "day";
  wrap.style.display = day ? "flex" : "none";
  altHost.style.display = day ? "none" : "block";
  if (day) { renderPool(); renderCanvas(); renderAside(); }
  else renderTimeView(altHost, viewMode, curDate, zoom);
}
function renderAll() { syncView(); }
…
const un = S.subscribe(renderAll);
```

七种视图共用这一个 `syncView()`；卸载时把反订阅函数缓存在容器节点上（`container._unsub`），
由外壳统一调用。这条规则 v0.58.0 由一次明确修正确立（设计篇 4.3 记的是规则，这里记的是它的成因）。

## 2. 几何与坐标系：算得对，还要画得对

### 2.1 渲染排序键与写回排序键必须逐位一致 🔴

**现象**：把卡片拖到某张卡"前面"，松手后它跑到了别处，或者直接落回原位。

**根因**：拖拽落点写回的是**数组下标**，而界面显示的是**排序后的顺序**。两套排序键少一位或多一位，
"插到相邻卡前面"这个判断就在 DOM 序与数据序里落到不同位置。

**解法**：`moveTaskRelative()` 里回填 `order` 的基准，逐字符复用 `tasksOfQuad()` 的排序键，
并且这个一致性是**踩坑之后写进注释**的（`store.js:240-246`）：

```js
// seq 排序键必须与 tasksOfQuad 完全一致（done→order→due，无尾键、稳定排序保持数组序）：
// 首次回填 order 的基准 = 渲染序，否则「插到相邻卡前面」在 DOM 序与 store 序里落点不同
// （实测探针抓到：createdAt 尾键让回填基准与 DOM 错位，拖拽落点跳位）
const seq = group.sort((a, b) => Number(a.done) - Number(b.done) ||
  ((a.order ?? Infinity) - (b.order ?? Infinity)) ||
  (a.due || "9999").localeCompare(b.due || "9999"));
seq.forEach((t, i) => { t.order = i; });
```

排序规则三层：**完成态永远沉底 → 显式 `order` 优先 → 无 `order` 者按截止升序**（`store.js:222-228`）。
`order ?? Infinity` 让老数据（从没拖过、没有 `order`）自然退回截止日排序，不需要迁移；
`order` 只在该象限**首次发生拖动**时批量回填 0..n-1，没被打乱过的列表不写冗余字段。

**怎么锁住**：`scripts/test-ui-scale.mjs` / 拖拽行为断言里核对两处排序键文本一致。

### 2.2 拖拽落点判定不能读 rect

**现象**：拖动过程中让位动画进行到一半时松手，插入槽判错。

**根因**：`getBoundingClientRect()` 在 FLIP 动画进行中会包含残余 `transform`，量到的是**动画中间态**，
不是布局终态。

**解法**：启动时缓存每张卡的高度和行间距，判定用几何递推（`views/quadrant.js:117-135`）：

```js

  const all = [...list.children].filter((c) => c.classList.contains("tkc"));

  const mids = all.map((c) => {

    acc += (st.h[c.dataset.id] || c.offsetHeight) + st.gap;
    return m;
  });
  …
```

（列表顶边只量一次，那是没有 transform 的容器；卡片高度全部走缓存。）
让位动画本身用 WAAPI 做 FLIP，先量终点差值再反向补一段位移（`quadrant.js:150-154`）：

```js
cards.forEach((c, i) => {
  const dy = before[i].top - c.getBoundingClientRect().top;
  if (dy) c.animate([{ transform: `translateY(${dy}px)` }, { transform: "none" }],
    { duration: 180, easing: "cubic-bezier(.22,.8,.22,1)" });
```

### 2.3 鼠标与触摸是两种意图：两套阈值 + 一次让路

**现象**：手机上想滚动列表，结果把卡片拖起来了。

**解法**：同一套 Pointer 事件，**进入拖拽的条件分开**（`quadrant.js:230,244,247`）：

- 鼠标：位移 `Math.hypot(dx, dy) >= 6` 即进入拖拽；
- 触摸：长按 240 ms 才进入（`pd.longTimer = setTimeout(…, 240)`），其间任意轴位移 `> 8` 就
  `clearLong(st)` —— 判定为"这是滚动意图"，直接取消待触发的拖拽。

还有一处跨事件顺序的补丁：手势会话期间置 `document.body.dataset.swipeSuspended = "1"` 让外壳的
"滑动返回"让路，而**清除要延迟 80 ms**，因为 `pointerup` 先于 `touchend` 发出，早清会在
`touchend` 判定之前就把让路撤了（`quadrant.js:73-75` 说明，`:99-100` 实现）。

### 2.4 CSS `zoom` 是布局级的：指针坐标必须除以生效系数 🔴

**现象**：把时间块画布放大到 150% 之后，拖动的落点比手指位置"偏一半"；
再把"界面缩放"调到 150%，偏移方向又变了。

**根因**：`zoom` 参与布局，`clientY` 与 `getBoundingClientRect()` 给的是**物理像素**，
而时间块的内联 `top/height` 写在**未缩放的空间**里。而且系数是**两层乘积**：
本视图的捏合系数 × 全局界面缩放系数。只除一层，就是原来那个 bug。

**解法**（`views/timeblock.js:112-115`）：

```js
const viewScale = () => zoom.get() * (Number(getComputedStyle(document.documentElement).getPropertyValue("--ui-scale")) || 1);
const minFromY = (y, rect) => Math.round(((y - rect.top) / viewScale() - 10) / PX_PER_MIN / 15) * 15 + DAY_START;
```

三处"屏幕 Y → 分钟"（点击放置、拖动块、改时长）统一走 `minFromY()`，不再各写各的。
除完还要落回 15 分钟网格，吸附与换算在同一行完成。

### 2.5 「恒定物理长度」的写法契约：`calc(Npx / var(--ui-scale))`

**背景**：2.4 的坑在 CSS 侧有同一个孪生问题。全局缩放写在 `documentElement.style.zoom` 上
（`uiScale.js:334-343` 的 `paintFactor()` 是唯一出口，同帧写入 `--ui-scale / --ui-auto-scale / --ui-vw / --ui-vh`），
于是 CSS 里"逻辑 px"和"物理 px"分裂成两套。

**契约**（`uiScale.js:331-333` 原文警告）：

> 想表达「恒定的物理边距」要写 `calc(Npx / var(--ui-scale))`；
> v0.48.0 曾写成 `calc(var(--ui-vh) - N)`，那等价于「距屏幕顶 N」，是错的。

错在哪：`--ui-vh` 是"视口长 ÷ 系数"的**布局长度**，从它里面**减**一个常数，减出来的位置离屏幕底
还有一整个视口那么远。这类 bug 不报错、不改功能，只在特定缩放下看起来"位置怪"，
所以它一旦成立就会被复制粘贴到很多处。

**已确立的应用点**：需要"按屏幕物理尺寸定位"的浮层，以及主题切换的圆形揭示动画 ——
它的圆心来自 `pointerdown` 的 `clientX/clientY`（屏幕 CSS px），而 `::view-transition` 伪元素活在
**zoom 之后**的坐标系（它的盒 = 视口 ÷ zoom），不换算圆就画在真实位置的 `1/zoom` 处。
这条契约现在由四条 CSS 断言守着：`scripts/test-theme-transition.mjs:266-271`
要求揭示几何的三个量各自除以 `--ui-scale`，且必须带 `1` 兜底
（`--ui-scale` 尚未写入时 `calc` 非法会让整条 `clip-path` 被丢掉 —— 表现是"动画没了"，而不是"动画错了"）。

### 2.6 窗口几何 API 必须成对：`innerSize ↔ setSize`、`outerPosition ↔ setPosition` 🔴

**现象**：桌面端"缩放视图"按钮（把窗口收成 1600×1100 并居中，再按还原），
每按一轮还原，窗口就比上一轮小一圈。

**根因**：Tauri/tao 在 Windows 上这四者的语义**不是对称的**（`src/windowSize.js:173-202` 的记录）：

| 前端 API | 落到 tao | 取的是 |
|---|---|---|
| `setSize` | `set_inner_size` | **内容区**（还会自己补投影边距） |
| `innerSize` | `client_rect` | **内容区** |
| `setPosition` | `set_outer_position` | **外框** |
| `outerPosition` | `get_window_rect` | **外框** |

无边框窗口（`decorations: false`）带一圈隐藏投影边距。用 `outerSize()` 取、喂给 `setSize()`，
等于每轮多减一次投影边距 —— 按十次窗口就没了。所以快照必须**成对**取、成对写：

```js
await win.setSize(new PhysicalSize(saved.inner.width, saved.inner.height));
await win.setPosition(new PhysicalPosition(saved.outer.x, saved.outer.y));
```

还有一处易被忽略的分支：缩放期间用户手动最大化过，还原时必须先 `unmaximize()`，
否则 `setSize`/`setPosition` 会被系统静默忽略（`windowSize.js:195-198`）。

### 2.7 画布宽度写死 vs 内容宽度：年表叠字

**现象**：横向时间轴（年表）里一排日期徽章只看得见「2026-0」，上下两排卡片互相压住。

**根因**（不是某条 CSS 写错，是两条几何约束叠加）：画布 `min-width` 写死 1500px，位置按**百分比**预算，
26 条事件分到 53px 一槽，而卡片宽 150px。上下两排的日期徽章还**都骑在同一条轴带上**，
相邻徽章只隔一槽 —— 70px 宽的徽章进 53px 的槽，后一张盖掉前一张后半截。
**百分比预算再怎么调都救不回「槽宽 < 内容宽」**，只能从画布宽度这一层解（`views/timeViews.js:495-507`）：

```js
const AXIS_BUDGET = 89;
const CANVAS_MIN = 1500;
const CARD_W = 150;                 // 与 .chronicle-event 的 --tl-card-w 同源
const SLOT_MIN = (CARD_W + 18) / 2;
const GAP_MIN = 120;                // 一枚省略号芯片占的横向位置
const TAIL_MIN = 46;                // 段尾安静带：徽章半宽 + 与芯片的间隙
const canvasW = Math.max(CANVAS_MIN, ((events.length - 1) * SLOT_MIN + gaps.length * (GAP_MIN + TAIL_MIN)) * 100 / AXIS_BUDGET);
const pct = (px) => px * 100 / canvasW;
const MIN_STEP = pct(SLOT_MIN);
```

`SLOT_MIN` 的推导是"同侧相邻卡隔两槽"：卡片 150 + 缝 18 ⇒ 一槽至少 84px。
宽度挂 `.chronicle-canvas` 的内联 **`min-width`**（不是 `width`），事件少时仍能铺满面板，多时横向滚动。

### 2.8 槽宽为什么必须是常数：不随「文字大小」变

**现象**：如果槽宽按渲染时读到的字号算，改完字号后画布会**重新叠出 14px**。

**根因**：文字缩放走的是 CSS 变量，`styles.css` 里改字号不触发这些视图的重渲染
（`tide:ui-preferences-changed` 全仓库没有监听方）。任何"渲染时读一次 CSS 变量"的算法，
都会在改完字号后留下一张按旧变量算出来的画布。

**解法**：槽宽取常数，徽章恒写 `MM/DD`（跨年把年份换成徽章内第二行，而不是加日期前缀 ——
前缀会把徽章拉宽一倍，而槽宽是按 `MM/DD` 算的）。**几何预算不依赖会被用户改掉的量**，
这是 2.7 成立的前提。

### 3.1 中文时间解析：单趟正则优先级表，不是文法

**现象**：校园场景的句子是"下周三下午 3 点开题组会""明天晚上 8 点交"这类 ——
相对时间、口语化、带量词。通用解析器要么报错，要么时间对了任务名丢了。

**解法**：`src/timeParser.js` 的 `parseWhen()`（4-138 行）是一张**优先级表**，而不是文法。三个关键设计：

**① 先做语义归一再解析**（`timeParser.js:9-13`）。"今晚 8 点"若直接解析，"今晚"被当日期吃掉后
时间词就孤立了，8 点会被当成早上 8 点：

```js
text = text
  .replace(/今(天|日)?晚(上)?/g, "今天 晚上")
  .replace(/明(天|日)?晚(上)?/g, "明天 晚上")
  .replace(/(今|明|后)早(上)?/g, (m, c) => (c === "今" ? "今天 上午" : c === "明" ? "明天 上午" : "后天 上午"));
```

同时首行还做了全角数字转半角（`:5-7`），避免"８点"解析不出。

**② 日期按 7 级严格优先级**（`:29-69`）：相对日 → 完整年月日 → 月日 → 星期 → 下月 X 日 → 月底 →
裸"X号"。第一个命中的级别独占，不合并 —— 合并会把"3 月 5 日"读成"5 号"。跨年/跨月做顺延：
`mkThisYear()`（`:21-26`）遇到已经过去的"3 月 5 日"自动滚到明年；裸"X号"同理（`:61-68`）。

**③ 时段词可以被结束时间继承**（`:94-118`）。出现"到/至/~/—"时第二个时间作为结束，
若它没有自带时段词，就继承开始时间的：

```js
// 「下午3点到4点」：结束时间继承开始时间的时段词
if (!times[1].period && times[0].period) {
  const p = times[0].period;
  if ((p === "下午" || p === "午后" || p === "傍晚") && eH < 12) eH += 12;
  else if ((p === "晚上" || p === "夜里" || p === "晚") && eH <= 11) eH += 12;
  else if (p === "中午" && eH <= 2) eH += 12;
}
endMin = eH * 60 + eM;
if (endMin <= startMin) endMin = null;   // 负时长宁可不写结束
```

12 类时段词映射到 24 小时制，分钟支持"半/一刻/三刻/X分"。

### 3.2 命中的时间词必须从标题里"吃掉"

**现象**：任务标题里残留"11:40"这类时间片段。

**解法**：解析过程中每个被消费的片段都进 `eaten` 数组，标题清洗时逐个剔除，再剥客套词与残留标点
（`timeParser.js:15-18, 120-135`）：

```js
// 兼容两种形态：正则匹配对象取 m[0]，时间条目取 .text
const eat = (m) => { if (m) eaten.push(m.text ?? m[0]); return !!m; };
```

统一一个 `eat()` 而不是每处各自记，是为了"日期分支吃正则对象、时间分支吃条目对象"两种形态
不会漏一半。剔完不足 2 字则回退用原文截断（保证标题永不为空）。

**明确的局限也在源码里记账**（设计篇 5.5）：不支持"昨天/前天"回溯、不对裸"3 点"做上下午推断、
不解析"预计 1 小时"这类时长（回落默认 60 分钟）。**已知不做的，比宣称做到的更需要写下来。**

### 3.3 同一套规则在 iOS JavaScriptCore 上过不了

**现象**：桌面端的"X号"判定用了后行断言 `(?<![0-9年月/.])(\d{1,2})\s*[号日](?!\d)`
（`src/timeParser.js:39`），小程序在 iOS 上**模块加载即抛语法错误** —— 不是解析错，是整个文件编译不过。

**解法**：iOS 16.4 以下的 JavaScriptCore 不支持 lookbehind，小程序侧改用捕获组 + 截断做等价改写，
匹配行为与原版一致（`miniprogram/core/timeParser.js:6-8` 原文注记）：

```js
// 小程序兼容性注记：原版的「X号」判断用了正则 lookbehind（(?<!...)），
// iOS 16.4 以下的 JavaScriptCore 不支持，会在解析模块时直接抛语法错误，
// 因此这里改用捕获组 + 截断的方式，匹配行为与原版一致。
```

这是三端同源里**唯一一处**规则级差异，值得单独说明：同源移植的代价不在算法，在运行时能力差异；
把它写成注释而不是口头默契，下一次移植的人才会绕开。

### 3.4 提醒不能用轮询：链式精准唤醒

**现象**：固定 1 秒轮询在空闲时一天白醒 86400 次；固定 60 秒轮询又让"提前 10 分钟"这一档
在整分钟边界上抖动。

**解法**：每次 tick 结束后按"下一个最近的提醒时刻"设定下一次延时，未来无提醒时退化为最长 5 分钟
巡检一次，并夹一个 1 秒下限防止忙循环（`taskReminder.js:301-308`）：

```js
function nextReminderDelay(tasks, now = Date.now()) {
  let next = Infinity;
  for (const p of reminderPoints(tasks)) {
    if (p.at > now && p.at < next) next = p.at;
  }
  // 没有临近提醒时最多每 5 分钟巡检一次；有提醒则精准唤醒。
  return Number.isFinite(next) ? Math.max(1000, Math.min(300000, next - now)) : 300000;
}
```

`schedule()` 每次先 `clearTimeout` 再设，所以任何状态变化后 250 ms 就能重新装弹
（`S.subscribe(() => schedule(250))`，`:338`）—— 改截止日期即刻生效，不等下一轮。
页面从后台切回可见时立即补一次巡检（`:337`），因为后台标签页的定时器会被浏览器节流。

**到点判定、下一次唤醒、原生排期三处共用同一个 `reminderPoints()` 生成器**（`:116-125`），
避免三处各算一遍算出三套结果。

### 3.5 补偿窗 90 秒 + 幂等键 🔴

**现象**：两类相反的抱怨同时成立 —— 主线程被一次重渲染挡住几百毫秒，提醒就**永久漏掉**；
而手机锁屏几小时后再打开应用，历史提醒**集体轰炸**。

**解法**：判定不是"到没到点"，而是"过了多久"（`taskReminder.js:86-98`）：

```js
for (const offset of taskOffsets(task)) {
  const at = due - offset * 60000;
  if (now >= at && now - at <= windowMs) out.push({ task, offset, at, due, key: `${task.id}:${due}:${offset}` });
}
```

默认窗口 `windowMs = 90000`：短任务阻塞后仍能补发，长时间错过的不追发。
每个提醒点带**幂等键** `任务id:截止时刻:提前量`，命中即写入已发日志（`:323-331`），
所以"改一次标题"不会让同一档提醒再响一次；日志按 90 天清理，不会无限膨胀。

提前量取值钳制在 0—43200 分钟并去重排序（`normalizeOffsets()`，`:61-63`），
长鸣上限只认预设档位（`:56`）—— 手改坏数据（0 / 负数 / 超大）会让长鸣要么立刻停、要么停不下来。

### 3.6 Android：WebView 没有 Notification API，网页定时器不跨进程 🔴

这是本篇最"硬"的一条，也是应用被划掉之后提醒还能响的唯一原因。

**现象**：手机上应用内横幅与提示音都正常，但**下拉栏里什么都没有**，应用被划掉后到点毫无动静。
用户以为"提醒功能坏了"，而界面上看不出任何异常。

**根因**（`src-tauri/src/notification.rs:3-12` 与 `src/api.js:248-257` 都记了这件事）：

1. **Android WebView 不实现 Web Notifications API**，`window.Notification` 压根不存在；
   桌面端 WebView2 同样没有 —— 所以 `taskReminder.js` 里那句权限判断在两端都是死分支；
2. 网页定时器**不跨进程存活**，应用被系统回收后，3.4 那套精准唤醒跟着消失。

⇒ 「应用不在了也到点响」只能交给原生 `AlarmManager`，"进下拉栏"只能交给原生通知。

**分层**（三层各管一段，谁都不越界）：

```
taskReminder.js   只管"什么时候该响、响什么"（业务概念都在这层）
androidNotify.js  只管通道：是不是 Android / 命令怎么发 / 失败怎么兜底（不知道任务、提前量）
notification.rs   一个 command 带 action 的路由（非 Android 恒返回 {applied:false}，不报错）
Kotlin            NotificationPlugin + ReminderHub + 三个 BroadcastReceiver
```

原生侧从 WebView 到系统组件的完整链路（含"应用被杀之后"那条唤醒路径）：

![Android 适配链路](architecture/07-android.svg)

**① 桥：数据形状对齐，平台差异在 Rust 吸收。** `src/androidNotify.js:21-31` 的 `call()`
把非 Android 与"原生桥缺失"（旧 APK 升级上来、或 `gen/android` 被 `tauri android init` 重建过丢了 Kotlin）
统一吞成 `{applied:false}`：

```js
async function call(action, payload) {
  if (!isAndroidRuntime()) return { ...OFF };
  try {
    const r = await api.notification(action, payload);
    return r && typeof r === "object" ? r : { applied: true, raw: r };
  } catch (e) {
    // 原生桥缺失时绝不能把调用方一起打断：提醒的兜底路径永远是应用内 toast。
    return { applied: false, error: String(e?.message || e) };
  }
}
```

**② 排期：整份重推 + 签名去重。** 事实源永远是网页里的 `data.json`，原生那份只是投影。
纯函数 `upcomingAlarmPlan()` 把提醒点折算成排期列表（`taskReminder.js:166-174`），
上限 40 条与 Kotlin 侧 `MAX_SCHEDULED` 对齐、只排未来 14 天：

```js
return [...reminderPoints(tasks)]
  .filter((p) => p.at > now && p.at - now <= ALARM_HORIZON_MS)
  .sort((a, b) => a.at - b.at)
  .slice(0, ALARM_MAX_COUNT)
  .map(reminderRecord);
```

整份推送前比一次 JSON 签名（`:176-186`）—— 否则每次输入都在跨进程刷一遍闹钟。

**③ 闹钟：精确与非精确两条路，且不补发。** `ReminderHub.kt:288-302`：

```kotlin
fun schedule(ctx: Context, rec: ReminderRecord) {
  val am = alarmManager(ctx) ?: return
  if (rec.at <= System.currentTimeMillis()) return
  try {
    val pi = alarmIntent(ctx, rec.key)
    if (canScheduleExact(ctx)) {
      am.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, rec.at, pi)
    } else {
      // 没给精确闹钟授权：setAndAllowWhileIdle 仍会在 Doze 的维护窗口里醒来，
      // 代价是最多晚几分钟。前端会把这个降级状态显示出来引导用户去开。
      am.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, rec.at, pi)
    }
  } catch (_: Throwable) { }
}
```

两句注释各挡一个坑：**已过点的直接跳过**，因为补发是网页侧 90 秒窗口（3.5）的职责 ——
原生也补的话，重启一次会把历史提醒全炸一遍；**降级要可见**，`status` 里带 `exact` 回给前端，
设置页显示"提醒可能会晚几分钟"，而不是让它静默退化。

**④ 两条触达路径共用同一个 key。** 这是"不会弹两条"的机制前提
（`ReminderHub.kt:63-79` 类注释，`idOf()` 用 `key.hashCode()`，`:121`）：

- 应用被杀：`AlarmManager` → `ReminderAlarmReceiver` → 读持久化记录弹通知，
  声音用系统闹铃（`TYPE_ALARM`，走闹钟音量通道，静音键管不着）；
- 应用活着：网页定时器命中 → 调 `post` 命令，**同一个 key** 重发同一条通知，
  于是上面那条被就地**升级**成常驻 + 「停止响铃 / 标记完成」两个按钮，而不是多出一条。
  持续长鸣由网页 Web Audio 循环负责。

**⑤ 开机恢复。** `AlarmManager` 的排期不跨重启（`ReminderReceivers.kt:71-85`）：

```kotlin
class ReminderBootReceiver : BroadcastReceiver() {
  override fun onReceive(context: Context, intent: Intent) {
    when (intent.action) {
      Intent.ACTION_BOOT_COMPLETED,
      Intent.ACTION_MY_PACKAGE_REPLACED,
      "android.intent.action.QUICKBOOT_POWERON" -> ReminderHub.restoreFromStore(context)
    }
  }
}
```

不接这个广播的后果是：手机重启之后所有提醒**静默失效**，直到用户某次真的打开应用才恢复。
三个动作一起监听：`ACTION_BOOT_COMPLETED` 管重启，`ACTION_MY_PACKAGE_REPLACED` 管覆盖安装
（覆盖安装同样会清掉排期，这一条最容易漏），`QUICKBOOT_POWERON` 管部分厂商的快速开机通道。
`restoreFromStore()` 只重排 `at > now` 的记录（`ReminderHub.kt:319-324`），过期的一律丢弃。

**怎么锁住**：`test-android-notification.mjs:91` 要求三个接收器都在版本化镜像里，
`:103` 要求 `ReminderBootReceiver` 在 `AndroidManifest.xml` 里注册且 `exported="true"`
（不 exported 的话系统广播根本进不来）。

**⑥ 按钮点击可能发生在应用已死之后。** 所以不能用 Tauri 的插件事件（那要求网页活着且已注册监听），
必须落 `SharedPreferences` 队列，网页醒过来时取走（`ReminderHub.kt:335-345` 写入，
`ReminderReceivers.kt:42-68` 的接收器只做两件事：记一笔 + 立刻处理通知本身让用户按完就有反馈）。
前端 `drainNativeActions()`（`taskReminder.js:261-281`）在每次巡检、回前台、长鸣轮询时清一次队列，
**幂等键反解出任务 id** 才执行改状态 —— 队列里可能是几小时前的点击。

**⑦ 长鸣不能被 WebView 冻住。** `WebView.onPause()` 会挂起页面定时器，
而持续提醒的循环调度与"最长响铃"自动停 watchdog 全跑在这些定时器上 ——
用户一退后台或按灭屏幕，铃声响到一半静掉，"持续提醒"退化成一响即停。修法只有一句
（`MainActivity.kt:114-122`）：

```kotlin
override fun onPause() {
  super.onPause()
  if (ReminderHub.ringActive) {
    try { webView?.onResume() } catch (_: Throwable) { }
```

**⑧ 没授权要主动说。** Android 13+ 的 `POST_NOTIFICATIONS` 没给时，整条原生链路是哑的，
而用户在设置页里看不到任何异常（应用内照常响，很容易以为已经提醒过了）。所以启动时提醒一次

`:91,:103` 见上。再加一道 `sync-android-native.js --check`，保证这些文件真的进了 `gen/android`。

### 3.7 长鸣必须有三条停止路径

**现象**：一只关不掉的闹钟 —— 通知被折叠、系统静音、人在开车，按钮就是点不到。

**解法**：`startRing()` 的注释把三条路径写成契约（`taskReminder.js:192-200`）：
① 应用内横幅上的「停止响铃」；② 原生通知上的同名按钮（经 `drainNativeActions` 转回来）；
③ 到 `ringMaxMs` 自动停。三条同时在代码里落地：

```js
ring = { ev, banner, maxTimer: setTimeout(() => stopRing(), maxMs), poll: setInterval(() => { drainNativeActions(); }, 1000) };
```

还有一处很容易做错的收尾（`:230-232`）：停止时**不能直接撤销**常驻通知，要就地**静默降级**成
一条可滑走的普通通知 —— 常驻通知滑不掉，而内容留着是给用户回看"刚才到底到点了什么"。
`silent` 是必需的：换渠道重发会按新渠道再响一次铃，用户刚点"停止响铃"就又响一声，等于按钮没生效。
一次只响一条（新事件先 `stopRing({silent:true})` 换掉旧的），两条长鸣交叠时用户既听不清也关不掉。

### 3.8 零音频文件的提示音

**约束**：安装包目标"不到 10 兆"，往里塞几十种铃声不划算；但用户确实要"能选出自己听得出区别的声音"。

**解法**：7 种预设 + 1 种长鸣全部用 Web Audio **现场合成**，音效是一张声明表
（`src/sound.js:8-37`），每个音是 `{f 频率, t 起始, d 时长, g 音量, type 波形}`：

```js
{ id: "chime", label: "三音铃", note: "上行三音，较悦耳", tones: [
  { f: 659.25, d: 0.22 }, { f: 783.99, t: 0.16, d: 0.22 }, { f: 1046.5, t: 0.32, d: 0.42 },
] },
```

长鸣预设用 `loop` 而不是 `tones`：一个 `period` 内排完整段无缝循环，
**period 末尾刻意留白** —— 循环接缝落在静音上，否则每圈一声咔哒
（`:28-35` 注释；实现是把整段渲染进 `AudioBuffer` 再交 `BufferSource.loop`，`:152,180-184`）。
两处工程细节：`ctx.state === "suspended"` 时先 `await ctx.resume()`（`:108`，浏览器自动播放策略）；
起止各留极短指数斜坡避免爆音（`:118-120`）。

**顺带解掉的问题**：原生通知的声音怎么办？答案是复用系统默认闹铃（`TYPE_ALARM`），
既不必往 `res/raw` 塞资产、也不必扩 `sync-android-native.js` 去同步二进制，
而且正好是用户说的"默认时钟的提示音"（`ReminderHub.kt:80-85`）。

## 4. 不确定的输入：AI 与冲突都不许直接落库

### 4.1 规则优先、AI 兜底，并且**粘贴不走 AI**

**现象**：每次粘贴都调一次大模型，用户的感觉是"这功能在偷偷烧钱"。

**解法**：两条明确的成本闸门（`src/capture.js`）：

```js
// capture.js:214-218  文本的择优路径：规则优先，AI 兜底
async function handleTextSmart(text, fileName = "") {
  if (parseWhen(text).date) { handleText(text); return; }
  if (await tryAiIngest({ text, fileName })) return;
  handleText(text);
}
```

- 规则解析（3.1）免费、即时、离线可用；**只有它认不出日期时**才值得花钱（`:205-213`）；
- 粘贴的纯文本**不自动走 AI**（`:121-126` 原文注释：粘贴是最高频的动作）。
  AI 只留给"图片"与"显式拖入的文件"—— 拖入是刻意行为，用户愿意付这个成本。

**为什么可以这样分**：规则路径是确定性的，所以"解析即落格 + 提示条告知"就够；
AI 路径是不确定的，所以必须进预览面板逐条确认（设计篇 5.4）。

### 4.2 AI 的日期：格式对，但日子不存在 🔴

**现象**：模型返回 `2026-02-31`。`new Date(2026, 1, 31)` **不报错**，静默滚到 3 月 3 日 ——
于是一条幻觉日期悄悄变成"另一天的安排"，用户只会看到"我明明没安排这天，怎么有个块"。

**解法**：校验格式之后**回读比对**（`src/aiIngest.js:50-62`）：

```js
export function cleanIngestDate(v) {
  const s = String(v ?? "").trim();
  if (!/^\d{4}-\d{2}-\d{2}$/.test(s)) return "";
  const [y, m, d] = s.split("-").map(Number);
  const dt = new Date(y, m - 1, d);
  if (dt.getFullYear() !== y || dt.getMonth() !== m - 1 || dt.getDate() !== d) return "";
  return s;
}
```

同一套白名单钳制覆盖所有字段（`normalizeIngestEvent()`，`:154-` ）：`kind` 必须在枚举里、
象限钳到 1—4、时长取起止差而不是取模型自报的 `durMin`（注释原话："模型算出的 durMin 经常和它
自己对不上"）、结束不晚于开始就**不写结束**（宁缺一个字段，也不生成负时长的块）、
日期为空则整条降级进收件箱。**AI 的结果永不直接写库。**

### 4.3 冲突事前试算 + 候选顺序是产品语义

**现象**：自动排程如果"直接覆盖"，用户丢的是手工安排的固定日程；
如果只报"冲突了"，用户还得自己一块块挪。

**解法**：判定用**严格半开区间**，重叠不漏也不误伤（`src/scheduleConflict.js:24-31`）：

```js
return (blocks || []).filter((b) => {
  if (ignoreId && b.id === ignoreId) return false;   // 自身块可排除

```

候选时段以 15 分钟为步长向两侧扩散，但**正向偏移先入列**（`:54-60`）：

```js
// 优先找原时间之后，再找之前；距离相同则更早的排后面，减少"往回挪"造成错过。
pushIfFree(desired);
for (let delta = step; candidates.length < limit && (desired + delta <= maxStart || desired - delta >= dayStart); delta += step) {
  pushIfFree(desired + delta);
  if (candidates.length >= limit) break;
  pushIfFree(desired - delta);
}
```

于是给出的建议总是"最近的不晚于原意的空档"。**步长、上限 4 条、每个候选再吸附网格**都在同一段里，
中文捕获链路（`capture.js:132-139`）与时间块画布复用同一函数，不会出现"画布避让了、捕获没避让"。
一个空档也找不到时只提示，绝不覆盖（`preview.ok === false && alternatives.length === 0`）。

### 4.4 课程同步：只有可移动的块才让位

**现象**：把课程表展开成时间块时，用户手工安排的"晚上写论文 2 小时"可能被课程挤掉。

**解法**：区分依据只有一个 —— `taskId`（`automation.js:54-61`）：

```js

    if (!moved) { S.addBlock(b); conflicts++; } }

```

三个"不确定即不猜"的细节：**必须全部可移动**（`every`）才动手，混进一节固定日程就整体不动；
让位失败要把刚摘掉的块**原样放回去**（`S.addBlock(b)`）；让位后仍冲突则放弃写入并生成一条
`course-conflict` 的收件箱条目请人判断。前扫起点是课程结束时间、上限 22:00，与画布起点无关。

## 5. 可恢复性：机器动的手脚要能收回

### 5.1 删除即撤销 = 补偿写，不是事务

**解法**：先深拷贝任务及其**全部关联时间块**，删除立即生效，返回一个闭包负责放回
（`src/store.js:153-165`）：

```js
export function deleteTaskUndoable(id) {
  const task = taskById(id);
  if (!task) return null;
  const snapshot = JSON.parse(JSON.stringify({ task, blocks: state.blocks.filter((b) => b.taskId === id) }));
  removeTask(id);
  return () => {
    if (taskById(id)) return;                                     // 已在则不重复插
    state.tasks.unshift(snapshot.task);
    state.blocks.push(...snapshot.blocks.filter((b) => !state.blocks.some((x) => x.id === b.id)));
    invalidateBlockIndex();
    changed();
  };
}
```

没有事务机制，撤销能力来自"快照 + 幂等放回"两处去重（`taskById` 判存在、块按 id 过滤）。
界面表现就是删除提示条上的「撤销」按钮（`views/quadrant.js:61-64`）。
编辑与拖拽**不提供撤销栈** —— 这个风险由自动备份承担，是明确分工而不是遗漏。

### 5.2 自动化的账本：动手前存快照，环形留 120 条

```js
// automation.js:17-19
function snapshot(){return {tasks:clone(S.getState().tasks),blocks:clone(S.getState().blocks),inbox:clone(S.getState().inbox||[])};}
function log(rule,message,before=null){const a=cfg(); a.logs.unshift({id:S.uid('log'),at:Date.now(),rule,message,before});a.logs=a.logs.slice(0,120);S.touch();}

```

三份数据整体回滚，因此不需要"逆向操作"的实现（撤销"挪了 3 个块"不用算它原来在哪）。
日志只留 120 条：**快照体积换历史长度**，这是环形缓冲的理由而不是随手写的数。
不可撤销的记录（纯读取类）不带 `before`，撤销时明确抛"这条记录不可撤销"，不假装成功。

### 5.3 高版本数据：直接拒绝，不做猜测式解析

```js
// migrations.js:16-24
if (version > CURRENT_SCHEMA_VERSION) {
  throw new Error("数据来自更新版本，请升级 Le时间管理 后再打开");
}
while (version < CURRENT_SCHEMA_VERSION) {
  const migrate = MIGRATIONS.get(version);
  if (!migrate) throw new Error(`缺少数据迁移步骤：${version} → ${version + 1}`);
  state = migrate(state);
  version = state.dataSchemaVersion;
}
```

两个"抛错"都是刻意的：未来的数据形状我们不认识，猜着解析会**静默改写**用户数据；
迁移步骤缺失同理。位置也讲究 —— `initStore` 里这一句**在 `try` 之外**（`store.js:74-75`），
否则读盘失败的处理会把它一起吞掉，变成"静默换成种子数据"，那是最坏的失败方式。

### 5.4 删一个遗留字段，写在归一化里而不是写一次性迁移

`normalizeState()` 里那句 `delete next.settings.background;`（`store.js:57`）配了原因注释
（`:54-56`）：这个键里可能压着几百 KB 的 base64 图片；删在归一化处而不是写一次性迁移，
是因为它**同时覆盖"打开本地数据"与"导入旧备份"两条路径**，而且幂等 ——
归一化每次加载都跑，删一个本来就不存在的键没有副作用。
这条有断言：`scripts/test-store-cache.mjs:32` 直接判 `"background" in state.settings` 必须为假。

### 5.5 凭据天然不在备份里

`data.json` 是用户会导出、会推给另一台机的东西，所以**密钥类数据一律不落它**：
AI 服务密钥与插件凭据存在 Rust 侧的 AES-256-GCM 加密文件（`lib.rs` 的 vault 命令），
写的时候同样是"临时文件 + 原子改名"，并且对临时文件同样收紧权限（`lib.rs:425-431`、`:493-496`）。
插件侧通过 `tide.vault.*` 访问。结果是一条不需要解释的安全性质：**导出与备份天然不含凭据**。

## 6. 扩展与基建：让约定不会烂掉

### 6.1 缺权限要抛错，不要静默降级 🔴

**现象（真实事故）**：school-notice v1.3.0 的「登录配置」点了没反应 —— 界面上动作与提示**一起消失**，
看着像按钮坏了。

**根因链**（`scripts/test-plugin-permissions.mjs:3-10` 把它写在了文件头）：宿主 `requirePermission` 抛错，
而插件普遍把"报错"也交给 `tide.notify`，于是**错误提示自己又抛一次**（因为 `manifest` 里少了 `notify`），
两条一起没了。表面看是"按钮坏"，实际是声明缺一项。

**机制**（`src/pluginHost.js:44-48`）：`makeApi()` 每个方法第一行都是它，缺权限直接抛而不是静默降级 ——
让插件在开发期就暴露声明缺失。

```js
function requirePermission(man, pid, perm) {
  if (!isPermissionAllowed(man, pid, perm)) {
    throw new Error(`插件“${man.name || pid}”没有「${PLUGIN_PERMISSION_LABELS[perm] || perm}」权限`);
  }
}
```

**怎么锁住**：`test-plugin-permissions.mjs` 按 API 路径反查所需权限，扫 `public/plugins/*/main.js` 与
`manifest.json` 对账。有意思的一处实现：**权限表从宿主源码里抽**，而不是在测试里再写一份
（`:20-26`，用正则抠出 `PLUGIN_PERMISSION_LABELS` 的键）—— 否则"两处各写一份"这件事本身就会漂移。

**如实说明**：当前用户侧只有插件"开 / 关"，**不提供逐权限授权**（`pluginHost.js:38-42` 注释 v0.11.4）。
所以权限位的价值在可审计、可校验，不在交互式授权；同时它也不是安全沙箱（设计篇 6.6）。

### 6.2 版本号即缓存契约 🔴

**现象**：插件改了 `main.js`、`manifest.json` 的版本没动 → 用户那边"清单已升级、实际仍运行旧插件"。

**根因**：入口脚本走 `fetch`，WebView / 浏览器的强缓存按 URL 命中，代码本身没变过 URL。

**解法**（`pluginHost.js:90-109`）：把版本写进 URL 查询串当破缓存手段，代码缓存键同样含版本：

```js
const key = `${source}:${man.id}:${version}:${entry}`;
…
// 内置插件会独立升版本。入口 URL 必须带版本，否则 WebView/浏览器会长期命中
// 旧的 main.js 强缓存，出现"清单已升级、实际仍运行旧插件"的错位。
const url = `/plugins/${man.id}/${entry}?v=${encodeURIComponent(version)}`;
const res = await fetch(url, { cache: "no-cache" });
```

失败路径也管住了：加载失败的 promise 会从缓存里删掉（`catch (e) { codeCache.delete(key); throw e; }`），
否则一次网络抖动会把"失败的 promise"永久缓存下来。

### 6.3 插件抛错不能打挂外壳

**机制**（`src/shell.js:1187-1200`）：挂载时创建带 `data-plugin-id` 的容器，`render` 用 `try` 包住，
**返回的函数当清理回调**存进 `_unsub`：

```js
try {
  const cleanup = def.pluginView.render(box, { refresh: () => switchTo(targetId, undefined, { history: false }) });
  const stopPluginMotion = observePluginMotion(box);
  view._unsub = () => { stopPluginMotion(); if (typeof cleanup === "function") cleanup(); };
}
catch (e) { box.append(el("p", { class: "desc" }, `插件视图出错：${e.message}`)); }
```

一个坏插件的表现是"这个页面显示它自己的错误信息"，其余视图照常。
错误信息**就地显示而不是弹 toast**：toast 会被下一条覆盖，而用户需要对着它去修插件。

### 6.4 `gen/android` 会被整个重建 → 版本化镜像 + `--check` 🔴

**现象（最阴的一类）**：手机端某个功能静默消失。没有报错，桌面端一切正常。

**根因**：`src-tauri/gen/android/` 是 Tauri 的**生成目录**（gitignored），
`tauri android init` 会把它整个清掉 —— 而手机端真正干活的原生代码只活在那里。

**解法**：原生 Kotlin 与清单声明的**事实源放在版本化目录** `le-time-management/android/gradle/`，
由 `tools/sync-android-native.js` 幂等同步进 `gen/android/`，构建前跑 `--check`
（`MainActivity.kt:14-22` 的类注释就是这件事的告示牌）：

```kotlin
/**
 * ## 本文件是「版本化镜像」，不是生成物
 * `src-tauri/gen/android/` 是 Tauri 的生成目录（gitignored），**重新 `tauri android init`
 * 会把它整个清掉** —— 而手机端真正干活的代码只活在那里。
 * **改这份文件，不要去改 gen 里的副本**（改了会在下次同步时被覆盖，且提交不进 git）。
 */
```

`--check` 两侧都查：镜像缺文件、gen 里的副本与镜像不一致都直接失败
（`sync-android-native.js:136-145`），通过时输出
`✓ Android 原生代码与版本化镜像一致（Kotlin 与自有资源 / 清单权限与教务窗口与提醒接收器 / FileProvider 路径）`
（`:379`）。反向还有 `--capture`，用来把 gen 里的现状采纳为镜像；gen 里出现未纳入镜像的 Kotlin 会警告
（`:125`）。**这一条把"手机端功能静默消失"从一次线上事故，变成一次构建失败。**

### 6.5 一个命令带 action，而不是十个命令

**理由**（`src-tauri/src/notification.rs:14-19`）：Kotlin 侧 `@Command` 方法名就是路由键，
十个 Rust 命令只是把同一份路由表抄两遍，**改一边忘另一边的概率远高于只维护一张表**。
Rust 侧持一份 `KNOWN_ACTIONS`（`:36-45`），传错的 action 直接报错而不是静默无操作。

同族的另一条平台判断也值得记：退出握手那一组 Rust 代码**不能**加 `#[cfg(desktop)]` ——
`invoke_handler` 的命令列表没有平台门控，`quit_ack` 只在桌面存在时，Android 编译会断在
`cannot find macro __cmd__quit_ack`（`lib.rs:1566-1569`，v0.52.0 实测）。移动端无人调用它，零成本。

### 6.6 深色主题不是挑颜色，是解不等式

**约束**：15 套主题在深色模式下都要各自一套色板，且"文字与背景不能相似"。肉眼挑出来的值会被测出来。

**解法**：浅色是唯一事实源（`src/styles.css`），深色由 `tools/lib/theme-tokens.js` 按 WCAG 反解派生。
核心是一个亮度扫描（`:94-105`）：

```js
/* 保持色相与饱和度，从 floor 往上找「与 bgHex 对比度 ≥ target」的最低亮度。
 * 这就是「文字与背景不能相似」的机械化保证：解不等式，而不是挑颜色。 */
function toneForContrast(h, s, bgHex, target, { floor = 40, ceiling = 80 } = {}) {
  let best = hsl(h, s, ceiling);
  for (let L = floor; L <= ceiling; L += 0.5) {
    const cand = hsl(h, s, L);
    if (contrastRatio(cand, bgHex) >= target) return cand;
    best = cand;
  }
  return best;
}
```

`relativeLuminance` / `contrastRatio` 是 WCAG 的标准定义（`:77-92`）。产物 `theme-derived.css` 是生成物，
手改会被覆盖，所以 `gen-theme-dark.js --check` 在 `npm test` 与 `npm run build` 里各拦一道。
"深色模式"与"主题"因此是两个正交属性（`data-theme` + `data-theme-mode`），
CSS 里凡深色才生效的规则一律写 `[data-theme-mode="dark"]`。

### 6.7 Android 键盘避让：inset 要消费对地方，否则整屏黑 🔴

**现象**：手机上聚焦输入框，键盘弹出后**整屏只剩背景色**。

**根因**（`MainActivity.kt:89-100` 的 ⚠️ 注释）：`enableEdgeToEdge()` 即 `decorFitsSystemWindows=false`，
此模式下系统的 `adjustResize` 不再生效、默认 `adjustPan` 又只整体上移窗口而网页视口毫无变化。
而更早一版把 `--sab`（底部安全区）写成 `maxOf(bars.bottom, ime.bottom)`：键盘弹出时 `--sab` 被撑到
约 370px，`.view` 的 `padding-bottom`、toast、抽屉底栏全部跟着暴涨，页面被凭空撑长一大截，
`scrollIntoView` 把 WebView 滚进这段空白 —— 就是那屏背景色。

**解法**：两个通道分工 —— `--sab` **只代表导航栏高度**，键盘由 WebView 自己的 inset 监听器消费，
且用 `bottomMargin` 而不是 `setPadding`：

```kotlin
ViewCompat.setOnApplyWindowInsetsListener(webView) { v, insets ->
  val ime = insets.getInsets(WindowInsetsCompat.Type.ime())
  val lp = v.layoutParams
  if (lp is ViewGroup.MarginLayoutParams) {
    if (lp.bottomMargin != ime.bottom) { lp.bottomMargin = ime.bottom; v.layoutParams = lp }
  }
  // ime 已由我们消费：剥掉再往下传，防止子层级二次消费（WebView 无子级，纯防御）。
  WindowInsetsCompat.Builder(insets).setInsets(WindowInsetsCompat.Type.ime(), Insets.NONE).build()
}
```

**WebView 不尊重 `padding`**（网页铺满 view 边界），而其父容器是 FrameLayout，
`MATCH_PARENT` 高度会减去 `bottomMargin` —— 于是等于把网页视口压短。视口变矮之后的连锁反应全是现成的：
`resize` → `uiScale.js` 重算 `--ui-vw/--ui-vh` → 媒体查询与 fixed 浮层自动重排。

### 6.8 Android 安全区：`env()` 恒为 0，双路变量 + 一条"别写兜底值"的断言 🔴

**根因**：Edge-to-Edge 下状态栏/导航栏是透明浮层，Android 约定应用自己消费 `WindowInsets`；
而 **Android WebView 不实现 `env(safe-area-inset-*)`**，`viewport-fit=cover` 写了也没用，取值恒为 0
⇒ 那一整套 `padding-top: env(safe-area-inset-top, 0px)` 在手机上全部退化成 `0px`，
标题与状态栏图标（信号/电量）重叠。

**解法**：原生读真实 inset 注入四个 CSS 变量（`MainActivity.kt:184-210`），前端一律写双路形式：

```kotlin
val js = buildString {
  append("(function(){var s=document.documentElement.style;")
  append("s.setProperty('--sat','${top}px');")   // 四方向都要取：横屏挖孔在侧边
  …
}
```

```css
/* 对 */  padding-top: var(--sat, env(safe-area-inset-top, 0px));
/* 错 */  padding-top: env(safe-area-inset-top, 0px);   /* 手机上 = 0，直接压状态栏 */
```

Android 走注入值，桌面 / iOS 走原生 `env()` 兜底，两条路径互不干扰。
三个容易被"顺手优化"掉的细节，全部有断言守着（`scripts/test-android-layout.mjs:230-251`）：

1. **不能裸用 `env()`** —— 反向断言 `assert.doesNotMatch(css, /(?<!\))\benv\(safe-area-inset-[a-z]+,\s*0px\)(?!\))/`，
   并正面要求双路写法至少 15 处；
2. **`:root` 里绝不能给 `--sat` 等写默认值** —— 变量一旦有有效值，`var()` 的第二参数**永不生效**，
   iOS / 桌面的原生 `env()` 会被彻底废掉。判定前先剥注释，否则文件里那段说明性注释会被自己误伤（`:234-240`）；
3. **补注入**：`onPageFinished` 里清掉签名再发一次，因为新文档会重置内联样式（`MainActivity.kt:168-174`）。
   `applyInsets` 本身按 `$top|$bottom|$left|$right` 签名去重，避免每次 insets 回调都跨进程 eval。

同文件里另一条测试自曝的坑也值得一提：定位 `.topbar` 的规则时，全文件有 8 个 `max-width:760px` 查询，
必须按"哪一块里有 `.topbar`"来定位，不能取第一个 —— 否则断言落在错误的块上（`:242-243`）。

### 6.9 把「约定」写成断言：六类元校验

本仓库的测试里相当一部分不是功能测试，而是"防止某个默契被破坏"的**元校验**：

| 约定 | 断言在哪 | 破坏后的表现 |
|---|---|---|
| 三端版本号一致 | `tools/sync-version.js --check`（且是 `npm run build` 第一条命令） | 安装包带错版本号 |
| 深色主题由浅色派生 | `gen-theme-dark.js --check` + 对比度校验 | 深色模式下某些主题文字看不清 |
| 生成型插件的入口是产物 | `build-schedule-plugin.js --check` / `build-exam-calendar-plugin.js --check` | 改了 `model.js` 白改 |
| Android 原生代码进了构建目录 | `sync-android-native.js --check` | 手机端功能静默消失（6.4） |
| 插件权限声明覆盖真实调用 | `scripts/test-plugin-permissions.mjs` | 动作与提示一起消失（6.1） |
| 安全区必须走双路变量 | `scripts/test-android-layout.mjs` | 顶栏压状态栏（6.8） |

**共同点**：这些规则**无法靠代码审查长期维持**（改的人不在现场、失败是静默的），
所以一律下沉成"生成器 + `--check`"双件套，在 `npm test` 与构建前置各拦一次。

## 7. 这些难题的共同形状

复盘上面 40 条，反复出现的其实是四个动作：

**A. 静默失效优先怀疑「跨层假设」。** 本篇里最贵的几个 bug 都不是函数内部算错，而是两层的假设不一致：
`env()` 在 WebView 里恒为 0（CSS 假设 vs 平台实现）、`setSize` 的"内容区"语义（前端命名 vs tao 实现）、
`::view-transition` 活在 zoom 之后的坐标系（JS 坐标系 vs CSS 坐标系）、
`new Date` 吞掉不存在的日期（业务假设 vs 语言行为）、插件事件要求网页活着（桥的假设 vs 进程生命周期）。
**修法一律是"把假设写进注释 + 写成断言"**，而不是"记住它"。

**B. 探针先于修改。** 几乎每条几何类难题都有一个一次性探针脚本（`output/probe-*.mjs / probe-*.html`），
它给出的不是"看起来好了"而是数字：年表改造前是"1500px 画布 / 53.4px 槽 / 150px 卡片 / 49 对重叠"，
改造后是"2737px 画布 / 84px 槽 / 0 叠 / 0 叠"；主题揭示是"zoom=0.64 时按下点 (19.8, 540.8) →
伪元素收到 30.98px/844.97px → 绘制回屏幕正是 (19.8, 540.8)"。**没有量过的修复不算修好。**

**C. 单一出口 + 派生而非重复。** 状态出口 `changed()`、缩放入口 `paintFactor()`、
提醒点到 `reminderPoints()` 生成器、排序键两处逐字符一致、权限表从宿主源码里抽、
深色令牌从浅色反解、Rust 命令表只维护一张。凡是"两处要一样"的东西，最终都收成了"只有一处"。

**D. 把不确定输入钳制成结构化字段。** AI 的日期、插件的 `when`、手改坏掉的配置，处理姿势是同一个：
白名单 + 回读校验 + **宁可不写也不猜**。展示串与结构化字段分离（`when` 给人看、`date`/`time` 给机器用）
也属于这一类 —— 把展示串当日期写入会产出非法日期，进而让提醒**静默失效**，
这个坑在 `views/inbox.js:33-35` 以注释固化。

### 尚未解决（同样如实列）

| # | 位置 | 现状 | 为什么不顺手改掉 |
|---|---|---|---|
| 1 | 插件样式隔离 | 只有 `data-plugin-id` 容器标记，实际靠类名前缀规范 | 上 Shadow DOM / iframe 会切断插件对宿主 CSS 变量的取用，代价大于收益 |
